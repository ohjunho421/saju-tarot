# 포인트 충전 결제

## 설명

포트원 V2로 포인트를 충전한다. 요금·차감은 [point-system.md](./point-system.md) 참고.

## 환경변수 (서버, Railway)

| 이름 | 용도 |
|------|------|
| `PORTONE_API_SECRET` | 결제 조회·취소용 서버 키 |
| `PORTONE_STORE_ID` | 상점 ID (결제창에 넘김) |
| `PORTONE_CHANNEL_KEY` | 결제 채널 키 (결제창에 넘김) |
| `PORTONE_PAY_METHOD` | 채널의 결제수단. `CARD`(기본, 카드 결제사) 또는 `EASY_PAY`(카카오페이·토스페이 등 간편결제 채널) |
| `PORTONE_WEBHOOK_SECRET` | 웹훅 시크릿 `whsec_...` (교체 중에는 쉼표로 두 개까지) |
| `PAID_MODE` | `on`이면 모든 회원에게 요금 적용. 없거나 다른 값이면 모든 리딩 무료, 충전 닫힘 |
| `PAID_MODE_TEST_EMAILS` | 쉼표로 구분한 이메일. `PAID_MODE`가 꺼져 있어도 이 계정만 요금·충전 적용 (심사·점검용) |

- 앞의 세 개 중 하나라도 없으면 결제 API가 503을 돌려준다(리딩·잔액 기능은 그대로 동작).
- `PORTONE_WEBHOOK_SECRET`이 없으면 웹훅을 받지 않는다(503). 로컬 개발에서만 `ALLOW_UNSIGNED_WEBHOOK=1`로 서명 없이 받을 수 있다 — 운영에는 절대 넣지 않는다.
- 상점 ID·채널 키는 서버가 결제 준비 응답으로 내려 주므로 화면(Vercel) 환경변수는 필요 없다.
- 포트원 콘솔 웹훅 주소: `https://<서버 주소>/api/payments/webhook`
- 블로그치트키의 실연동 채널은 그 가맹점 계약 전용이다. 별사탕은 별도 전자결제 심사 후 자기 채널을 쓴다. 개발은 테스트 채널로 한다.

## 유료 전환 스위치 — `server/src/services/paid-mode.ts`

결제사 심사는 약관·요금·결제 화면이 배포돼 있어야 받을 수 있는데, 실결제 키는 심사가 끝나야 나온다.
그래서 배포와 유료 적용을 분리했다.

1. **배포 (`PAID_MODE` 없음)**: 리딩은 전처럼 무료다. 잔액 버튼·요금 표시·포인트 카드는 숨겨지고, 약관·방침·요금 안내 페이지만 보인다. 요금 안내에는 "유료 리딩은 준비 중" 문구가 뜬다.
2. **심사 (`PAID_MODE_TEST_EMAILS`에 심사용 계정 등록)**: 그 계정으로 로그인하면 요금·충전 흐름이 모두 보인다. 결제사에 이 계정을 알려 준다. 이때 `PORTONE_*` 키는 테스트 채널 것을 쓴다.
3. **출시 (`PAID_MODE=on` + 실연동 키)**: 모든 회원에게 요금이 적용된다.

- 스위치가 꺼져 있을 때 리딩 API는 요금을 0으로 처리하고 무료 사용 기록(`DailyFreeUse`)도 남기지 않는다. 충전 준비(`/payments/prepare`)는 503을 준다. 이미 만든 주문의 확인과 웹훅은 막지 않는다.
- 화면은 `GET /api/points/me`의 `paid`로 표시를 켜고 끈다. 가격표(`/points/prices`)의 `paidMode`는 요금 안내 페이지의 "준비 중" 문구에 쓴다.
- 테스트 채널 키로 `PAID_MODE=on`을 켜면 누구나 가짜 결제로 포인트를 받을 수 있다. **`on`은 실연동 키를 넣은 뒤에만 켠다.**

## 운영 DB 반영 방식 (2026-11-23 확인)

Railway는 `prisma db push`로 스키마를 맞춘다. 새 테이블·칸(`PaymentOrder`, `DailyFreeUse`, `termsAgreedAt`, `shortfall`)은 배포 때 만들어졌지만, 마이그레이션 SQL에만 있는 **기존 회원 1,000P 지급과 잔액 0 이상 CHECK 제약은 적용되지 않았다.** 유료 전환 전에 직접 실행한다 — [point-system.md](./point-system.md) 참고.

## 결제사 심사 준비 (2026-11-17 포트원 콘솔·안내 문서 기준)

- **KG이니시스는 사주·운세 업종을 받지 않는다.** 블로그치트키의 이니시스 채널은 쓸 수 없다. 운세는 여러 결제사에서 유의업종이라 개별 심사를 받는다.
- 가입비(계약 시 1회, VAT 별도): 갤럭시아머니트리·토스페이먼츠·KSNET·다날 등 대부분 200,000원, NHN KCP 150,000원, 한국결제네트웍스·KG이니시스 무료. 한국결제네트웍스는 운세 업종에 보증보험 100%를 요구한다고 안내돼 있다.
- 포인트 충전 방식: 포트원 고객센터의 위험업종 안내에는 갤럭시아머니트리·토스페이먼츠·나이스정보통신·KSNET·다날 등이 "심사 후 확인 가능", NHN KCP·스마트로·한국결제네트웍스는 "입점 불가"로 나와 있다. 충전 업종 공통 조건은 충전 금액 1천 원~10만 원, 환불은 결제한 수단으로 취소. 현재 구현(3,000·5,000·10,000원 충전)은 이 범위 안이다. 포트원 블로그 글은 충전 방식이 건별 결제보다 통과율이 낮다고 적고 있다.
- 운세 업종(사주/운세/타로): 같은 안내에서 갤럭시아머니트리·한국결제네트웍스·KG파이낸셜·헥토파이낸셜·NHN KCP·토스페이먼츠·나이스정보통신은 "심사 후 확인 가능", KG이니시스·키움페이는 "입점 불가". 다날은 단순 운세 사이트만, KSNET은 굿 비용 불가.
- 포트원 전자결제 신청의 **사전 점검**(신청 3단계)에 주소를 넣으면 요건을 미리 검사해 준다. 2026-11-17에 운영 주소(`saju-tarot.vercel.app`, 이번 변경 배포 전)로 돌린 결과: 접속·호스팅·불가업종은 통과, 사업자 정보·이용약관·개인정보처리방침·환불 정책·상품 등록은 "확인 필요", 위험업종(사주/운세) 해당. 배포 후 다시 돌릴 것.
- **간편결제 직접 계약은 가입비가 없다**(포트원 콘솔 가입비 표, 2026-11-17): 카카오페이·토스페이·페이코·스마일페이·Npay 무료. 위험업종 안내에서 카카오페이·토스페이는 사주/운세와 포인트 충전 모두 "심사 후 확인 가능", 네이버페이는 사주/운세 입점 불가. 간편결제 채널을 쓸 때는 `PORTONE_PAY_METHOD=EASY_PAY`. 채널은 한 번에 하나만 설정할 수 있다(여러 채널 중 고르는 화면은 없다).
- 사이트 요건: 하단에 상호·사업자등록번호·대표자명·사업장 주소·전화번호(휴대폰 번호 불가)를 메인과 결제 화면에 상시 노출, 이용약관·개인정보처리방침·환불 정보, 고정 금액 상품 1개 이상, 결제창 호출 구현. 상품명 TEST·0원 결제는 심사 불가.
- 주소에 test·dev·staging이 들어가면 일부 카드사에서 반려된다. `vercel.app` 주소의 허용 여부는 안내에 없다.
- 사업자등록증의 업종이 실제 서비스와 맞아야 한다. 2026-11-17 현재 등록 업종은 광고 대행업뿐이며 724000(데이터베이스 및 온라인 정보 제공업) 추가 정정신고가 임시 저장 상태다.
- 심사 때 안내할 주소: `/?page=terms`(이용약관), `/?page=privacy`(개인정보처리방침), `/?page=policy`(요금과 환불 안내).
- 사업자 정보는 `client/src/data/business.ts`에 넣는다(비어 있으면 화면에 나오지 않는다).

## 흐름

```
[화면] POST /api/payments/prepare { packageId }
       서버: 충전 단위 확인 → PaymentOrder(PENDING) 생성 → 주문번호·금액·상점 정보 응답
[화면] PortOne.requestPayment({ paymentId: 주문번호, totalAmount: 서버 금액 })
[화면] POST /api/payments/verify { paymentId }     ← 결제 직후. 승인 대기(202)면 3초 간격으로 최대 20번 다시 확인
[포트원] POST /api/payments/webhook                ← 결제 완료·취소 알림 (브라우저가 닫혀도 온다)
       서버: 주문 조회 → 포트원에서 실제 결제 조회 → 금액·통화 일치 확인 → 포인트 지급
```

- 주문번호(`bs_{시각}_{난수}`, 40자 이하)는 서버가 발급한다. 금액과 주문자는 DB의 `PaymentOrder`가 기준이다.
- 휴대폰은 결제창이 다른 페이지로 갔다가 `?paymentId=...`를 달고 돌아온다. `App.tsx`가 읽어 이어서 확인한다.

## 서버가 막는 것

| 시도 | 처리 |
|------|------|
| 결제창 금액을 낮춰 결제 | 주문 금액과 다르면 지급하지 않고 결제 자동 취소 |
| 결제창의 채널 키를 테스트 채널로 바꿔 모의 결제 | 결제된 채널이 `PORTONE_CHANNEL_KEY`와 다르면 지급하지 않고 자동 취소 |
| 남의 결제번호로 `/verify` | 로그인 계정의 주문만 조회 → 404 |
| 같은 결제를 verify와 웹훅이 동시에 처리, 웹훅 재전송 | `settleOrder`가 PENDING→PAID 전환을 한 번만 허용 → 포인트는 한 번만 지급 |
| 위조 웹훅 | 서명(Standard Webhooks) 불일치로 401. 본문의 이벤트 종류는 믿지 않고 포트원의 실제 결제 상태로 판단 |

## 결제 취소(환불)

- 사용자 환불 요청은 상담 채널로 받아 포트원 콘솔에서 취소한다(자동 환불 API 없음).
- 콘솔에서 취소하면 웹훅이 와서 `revokeOrder`가 지급했던 포인트를 회수한다. 이미 써서 잔액이 모자라면 남은 만큼만 회수하고 부족분을 `PaymentOrder.shortfall`과 로그(`미회수`)에 남긴다.
- 부분 취소는 자동으로 회수하지 않고 로그(`부분 취소된 결제`)만 남긴다 → 관리자가 확인해 처리한다.
- **취소 웹훅이 끝내 오지 않으면 포인트가 회수되지 않는다.** 지급된 주문을 포트원과 주기적으로 대조하는 작업은 아직 없다.

## 주의사항

- 자동 취소가 실패하면 `[결제] 자동 취소 실패` 로그가 남는다 → 포트원 콘솔에서 수동 환불.
- 채널 확인은 포트원 결제 조회 응답의 `channel.key`를 본다. **이 필드 이름은 실제 응답으로 확인하지 못했다** — 테스트 결제에서 정상 결제가 "주문과 다른 결제"로 취소되면 여기부터 볼 것.
- 채널이 수동 승인 방식(SDK가 `paymentToken`을 돌려주는 경우)이면 서버가 승인(confirm)을 호출해야 하는데 **아직 구현하지 않았다.** 실연동 채널을 붙일 때 승인 방식을 확인할 것.
- 포트원 응답 전체에는 결제자 개인정보가 있어 로그에 남기지 않는다(상태·금액만 꺼낸다).
- 결제 준비는 사용자별 10분에 10번, 결제 확인은 10분에 60번으로 제한한다(메모리 기반, 서버 재시작 시 초기화).

## 검증 상태 (2026-11-16)

- 빌드, 가격 계산·한국 시간 자정·웹훅 서명 검증은 확인했다.
- **실제 결제창을 통한 결제, DB를 거치는 차감·정산은 아직 실행해 보지 않았다.** 테스트 채널 키를 넣은 뒤 확인이 필요하다.
